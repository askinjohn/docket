What this product is

A local-first Gmail client you run on your laptop. Humans use an Angular UI in the browser on localhost. Agents use MCP. Mail, secrets, and index live in a local DB. AI is hybrid (local models + optional cloud keys). Not a multi-tenant cloud SaaS.

UI Local core SQLite Gmail AI MCP OS / optional shell

Angular 22 — what we use (stable only)

UI is Angular 22. Production code sticks to stable APIs. Scaffold with npx @angular/cli@22 (or latest 22.x).

WebMCP (experimental in Angular 22)

In-browser tools for browser-embedded agents. Interesting later, not our agent story. Agents use the local core MCP server (search_mail, get_thread, …). Keep those separate.

UI state pattern (Angular-native — no Zustand)

signal / linkedSignal → selection, layout, theme, command palette open httpResource / resource → threads, messages from local core Signal Forms → compose + settings @Service() → shared stores & API clients WebSocket/SSE → patch signals when core pushes new mail

Key flows

A. First launch & Gmail connect

Start backend→ Open Angular UI→ Click Connect Gmail→ OAuth in browser→ Redirect to localhost→ Core stores tokens→ Initial sync → SQLite

B. Read inbox (human)

UI requests threads→ Core reads SQLite→ Return list fast→ Open thread→ Body from cache or Gmail fetch→ Sandbox HTML render

C. Archive (optimistic Superhuman-style)

Press e→ UI hides thread now→ Core: remove INBOX label via Gmail→ Update SQLite→ Undo window optional

D. New mail → notification

Core poll/history sync→ Detect new thread→ Write SQLite→ Push event over WS/SSE→ Angular shows Web Notification

E. AI draft reply (hybrid)

UI: “Draft reply”→ Core loads thread from DB→ Pick provider (local/cloud)→ Optional MCP context→ LLM returns draft→ UI compose box

F. External agent via MCP

Cursor / Claude / etc.→ MCP: search_mail→ Core queries SQLite / Gmail→ Structured result→ Agent reasons (no browser needed)

Notifications

Yes — quality depends on how “alive” the core and UI are.

v1 Browser Web Notifications

  • User grants permission once
  • Core emits mail.new over WebSocket/SSE
  • Angular calls Notification API
  • Click focuses tab / opens thread

Works well when browser is open. Weaker if browser fully quit.

Later Native path

  • Core stays running (login item / menubar)
  • Native notifier or Tauri/Electron/Swift shell
  • Notification Center even without a tab
  • Optional Dock badge

Same core events; different delivery adapter.

MCP & AI (both built into core)

MCP server Expose mail

Other agents call your laptop:

  • search_mail — query / FTS / Gmail q=
  • get_thread — full conversation
  • list_labels / views
  • draft_reply — create draft (confirm policy TBD)
  • archive / star — mutations with safeguards

Backed by the same SQLite + Gmail as the Angular UI.

MCP client Consume tools

In-app AI can pull external context:

  • Filesystem / notes MCP
  • Calendar, browser, git, …
  • Configured list of servers in settings

Example: “Draft reply using my project notes” → mail + notes tools.

AI hybrid routing

UI or MCP request │ ▼ AI orchestrator │ loads thread + policy + optional MCP context ├── privacy/simple → local model (Ollama…) ├── hard/quality → cloud model (user API key) └── offline/no key → local only or clear error │ ▼ result → UI compose / MCP response / notification

Where does Swift fit?

Swift is optional packaging, not the center of the design you chose.

Approach Role of Swift Fits AI + MCP + Angular?
Browser plan (chosen lean) None required Best fit
Swift shell only Window, menu bar, native notifications; embed or open Angular Good later upgrade
Full SwiftUI app Entire UI in Swift; core may still be separate Rebuilds Superhuman UI; Windows later hurts; MCP ecosystem thinner

Rule of thumb: keep mail + AI + MCP + DB in the local core. Swift (or Tauri) only if you want a Dock citizen and stronger notifications.

Trust & security boundaries

Must stay in core / OS

  • Gmail refresh tokens
  • Cloud LLM API keys
  • Destructive mail tools over MCP (policy)
  • DB file permissions (user home)

Browser rules

  • Talk only to 127.0.0.1
  • Sandbox email HTML (no random JS)
  • Remote images: user preference / proxy later
  • Never bind core to public interfaces by default
